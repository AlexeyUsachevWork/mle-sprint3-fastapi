# Соответствие EDA требованиям task.md

**Коротко:** по пункту EDA из `task.md` требования закрыты **уверенно**. Для ревьюера артефакт и выводы выглядят достаточными. Ниже — сверка по правилам проверки.

## Что требует task.md именно про EDA

| Требование | Ожидаемый артефакт | Статус |
|------------|--------------------|--------|
| «Проведите первичный анализ данных в Jupyter Notebook и опишите закономерности» | Notebook с EDA | **Есть** — `notebooks/01_eda.ipynb` с выполненными ячейками и outputs |
| В README: «Проведение EDA. Опишите ключевые шаги… Выделите основные выводы» | Раздел в README | **Есть** — раздел 3 с фактами и решениями |
| Посмотреть доступные данные кейса 1 (банк) | Работа с `train_ver2` | **Есть** — полный прогон ~13.6 млн строк |
| Предсказать **новые** продукты (доп. продукты в 2016) | Понимание таргета в анализе | **Есть** — явно разобран переход `0→1`, не просто ownership |
| `.csv` не в git | `.gitignore` | **Есть** (и EDA-артефакты тоже локально) |

Механизмы «порциями / parquet / slim» **task.md не требует** — это техника работы с объёмом. Для проверки важно не «как экономили RAM», а что анализ реальный, закономерности описаны и связаны с задачей.

## Насколько выводы «правильные» с точки зрения проверки

Сильные совпадения с постановкой кейса:

1. Данные — помесячные срезы → объект `(клиент, месяц)` — согласовано с описанием датасета.
2. Фокус на **покупках/открытиях новых продуктов** — прямо то, что просят в кейсе 1.
3. Выводы ведут к метрикам списка и time-split — это уже стык с блоком «трансляция» (тоже в README), ревьюер увидит связку EDA → постановка.
4. Есть конкретные числа и решения «что дальше» — это как раз то, что ждут в README про EDA.

Не является пробелом по task.md, но ревьюер может спросить:

- отдельный holdout vs весь valid янв–апр 2016 — в README это отмечено как опция, конфиг пока без жёсткого holdout;
- глубокий анализ связей «профиль → открытие» (корреляции age/renta с таргетом) — в EDA больше описательная статистика и таргет, чем feature–target зависимости; для *первичного* EDA обычно хватает;
- в ноутбуке много инфраструктуры чтения — ок, если выводы читаемы (сейчас ок и в notebook, и в README).

## Чего task.md от EDA **не** ждёт (и это не ошибка)

- DVC/MLflow/Docker внутри EDA
- готовый `model.bin`
- Airflow (это кейс 2)
- полный feature engineering в EDA-ноутбуке

Это следующие пункты таблицы артефактов (4–8), не пункт 1.

## Оценка для сдачи именно этого блока

| Критерий ревью | Оценка |
|----------------|--------|
| Есть Jupyter Notebook с EDA | Соответствует |
| Описаны закономерности | Соответствует (редкость таргета, дисбаланс, пересечение клиентов, пропуски, split) |
| Выводы в README | Соответствует |
| Связь с бизнес/техпостановкой кейса | Соответствует и даже сильнее минимума |
| Воспроизводимость прогона | Частично: код и `requirements.txt` есть; сами `data/processed/eda/*` в git не лежат (так и задумано) — ревьюер перезапустит или посмотрит outputs в ipynb |

**Итог:** для правил проверки из `task.md` блок EDA **соответствует** обязательным требованиям и хорошо стыкуется с формулировкой банковского кейса. Риски на ревью по EDA низкие; дальше по проекту остаются эксперименты, модель, API и мониторинг.

# Признаки и обучение (пункт 4) — что сделано и соответствие task.md

## Что сделано

1. Пайплайн:
   - `src/data/prepare.py` — пары t→t+1, чистка профиля, time-split, сэмпл клиентов
   - `src/features/build.py` — 43 признака (профиль + частоты категорий + портфель)
   - `src/models/train.py` — popularity baseline + LightGBM per-product, MAP@7 / Precision@7 / Recall@7
   - `src/models/metrics.py`, `src/constants.py`
2. Ноутбук: `notebooks/02_experiments.ipynb`
3. Артефакты: `models/model.bin` (~18 МБ), `models/metrics.json`
4. MLflow: run `bank-rec-train-001` в эксперименте `bank-product-recommender`
5. README §4 заполнен выводами прогона

| Baseline (популярность) | 0.0210 | 0.0057 | 0.0307 |
