# Рекомендатель банковских продуктов — итоговый проект

Рекомендательная система банковских продуктов: по профилю клиента и истории владения продуктами предсказываем, какие новые продукты предложить в следующем месяце.

## Цели
- EDA и подготовка признаков
- Эксперименты и трекинг в **MLflow**
- Версионирование данных/артефактов через **DVC**
- Веб-сервис рекомендаций на **FastAPI** в **Docker** (bind-mount моделей/данных)
- Мониторинг: **Prometheus** + **Grafana**

## Стек
Python, pandas, scikit-learn / LightGBM, MLflow, DVC, FastAPI, Docker Compose, Prometheus, Grafana.

## Руководство по проекту

### 1. Бизнес-задача → техническая задача и метрики

#### 1.1. Целевое действие

**Бизнес-цель:** предложить клиенту банковские продукты, которые ему с наибольшей вероятностью подойдут как *новые* (кросс-сейл), а не подтвердить уже имеющийся портфель.

**Техническое целевое действие:** для клиента `ncodpers` на месяц \(t\) предсказать продукты, которые в месяце \(t+1\) перейдут из отсутствия во владение — переход **`0 → 1`** по колонкам продуктов.

Колонки продуктов — бинарные флаги владения с именами вида `ind_*_ult1`. 
Примеры:

| Колонка | Продукт |
|---------|---------|
| `ind_cco_fin_ult1` | текущий счёт |
| `ind_tjcr_fin_ult1` | кредитная карта |
| `ind_hip_fin_ult1` | ипотека |
| `ind_nomina_ult1` | зарплатный счёт |
| `ind_recibo_ult1` | прямой дебет (recibo) |

Значение в строке месяца: `0` — продукта нет, `1` — продукт есть.  
Таргет строится сравнением соседних месяцев одного клиента: интересует только **первое появление** продукта (`0 → 1`). Переходы `1 → 1` (уже владеет) и `1 → 0` (закрыл) в целевое действие не входят.

Префикс/суффикс целевых колонок зафиксированы в `configs/train.yaml` (`data.target_prefix`, `data.target_suffix`).

#### 1.2. Техническая постановка

Задача звучит так: для клиента `ncodpers` (id клиента) на дату среза **t** (`fecha_dato`) нужно **расставить по приоритету до ~24 продуктов** `ind_*_ult1` — от более вероятного перехода `0 → 1` в месяце **t+1** к менее вероятному — и вернуть **топ‑K** продуктов, которых у клиента **ещё нет** на момент **t**.

Иначе говоря: не просто «возьмёт / не возьмёт» по каждому продукту отдельно, а **упорядоченный список рекомендаций** ограниченной длины (ранжирование нескольких продуктов сразу).

##### Единица обучения и предсказания

| Сущность | Содержание |
|----------|------------|
| Объект | пара `(ncodpers, fecha_dato = t)` — клиент в конкретном месяце |
| Признаки на момент t | только то, что известно на конец месяца **t** (без данных из будущего) |
| Правильные ответы на t+1 | для каждого из ≈24 продуктов: `1`, если он появился в **t+1** (`0 → 1`), иначе `0` |
| Предсказание | оценка (score) по каждому продукту → сортировка → убрать уже имеющиеся → топ‑K |

Один клиент даёт много объектов во времени (по одному на каждый месяц, для которого известен следующий месяц).

##### Вход модели (признаки на момент t)

1. **Профиль клиента** — относительно стабильные поля: `age`, `sexo`, `renta`, `segmento`, `nomprov` / `cod_prov`, `antiguedad` и т.п.  
2. **Текущий портфель** — значения всех `ind_*_ult1` на месяц **t** (что уже есть; эти продукты в ответе API не предлагаем).  
3. **Динамика (по возможности)** — сводки за прошлые месяцы: сколько продуктов было, недавние открытия/закрытия, значения портфеля в предыдущих месяцах. Так легче отличить «спокойных» клиентов от тех, кто активно подключает новые продукты.

##### Выход модели и что делаем после неё

1. Модель выдаёт **оценку (score)** для каждого продукта — насколько вероятен переход `0 → 1`. На практике это может быть одна модель с несколькими выходами или **отдельная модель «да/нет» на каждый продукт**; главное — получить сравнимые оценки.  
2. Продукты, которыми клиент уже владеет (`1` на **t**), **убираем** из списка.  
3. Остальные сортируем по убыванию оценки.  
4. Берём первые **K** позиций (`top_k`, по умолчанию 7 в `configs/train.yaml` / `configs/service.yaml`).

##### Почему список с приоритетом, а не «24 независимых да/нет»

- Каналу продаж нужен **короткий упорядоченный список** предложений (лимит звонка, пуша, баннера), а не 24 равноправных ответа без приоритета.  
- Метрики качества (MAP@K, Precision@K) как раз проверяют, хорош ли **ранжированный топ**, а не каждая модель сама по себе.  
- Отдельные модели «да/нет» по продуктам допустимы как способ **посчитать оценки**, но для бизнеса и сервиса итог всегда один: **отсортированный топ‑K**.

##### Почему не рекомендация «похожие клиенты купили то же»

В классических интернет-магазинах часто смотрят на плотный лог кликов и покупок («кто на что кликал»). У нас другие данные: **ежемесячные срезы** и **богатый профиль** (возраст, доход, сегмент), а новые продукты берутся редко. Поэтому естественнее обучать модели на **табличных признаках** клиента и портфеля (например, градиентный бустинг), а текущий набор продуктов использовать как часть этих признаков, а не строить систему только на «похожести» клиентов.

| Этап | Где | Что делает относительно постановки |
|------|-----|-------------------------------------|
| prepare | `src/data/prepare.py` | срезы, чистка, стыковка **t** и **t+1** для целевых меток |

#### 1.3. Метрики

Оцениваем не «угадал ли один продукт», а **насколько хорош короткий список из K рекомендаций**. По умолчанию **K = 7** (параметр `top_k` в `configs/train.yaml` и `configs/service.yaml`).

##### Почему K = 7

1. **Лимит контакта.** В одном звонке, пуше или экране обычно показывают не десятки продуктов, а короткий список. Диапазон 5–10 офферов типичен; **7** — разумная середина.
2. **Одна постановка для метрик и API.** Считаем MAP@7 / Precision@7 / Recall@7 и отдаём те же 7 позиций в сервисе — качество измеряем в том же сценарии, в котором модель будет работать.
3. **Масштаб задачи.** Продуктов около 24, а новых за месяц у клиента обычно мало (часто 0–2). Топ‑1 слишком жёсткий, топ‑24 бессмыслен для бизнеса; топ‑7 даёт запас, но остаётся коротким списком.
4. **Не жёсткая константа.** После EDA K можно сменить (например, на 5 или 10), если окажется, что клиенты в среднем берут больше или меньше новых продуктов — для этого `top_k` вынесен в конфиг.

Для каждого клиента на валидации сравниваем:
- **рекомендации** — топ‑K продуктов, которых у него ещё не было на месяц **t**;
- **факт** — какие продукты реально появились в **t+1** (переходы `0 → 1`).

##### Основные метрики (офлайн, логируем в MLflow)

| Метрика | Что измеряет | Зачем нужна |
|---------|--------------|-------------|
| **MAP@7** (главная) | Насколько удачен **порядок** в топ‑7: попадания выше в списке ценятся сильнее | Близка к сценарию «сначала предлагаем самое вероятное»; основная метрика для выбора модели |
| **Precision@7** | Какая доля из 7 предложенных продуктов реально появилась у клиента | Понятна бизнесу: «сколько из показанных офферов сработали» |
| **Recall@7** | Какую долю **всех** новых продуктов клиента мы поймали в топ‑7 | Контроль, что не упускаем нужные продукты, даже если их несколько |

Кратко на пальцах для одного клиента:
- факт: взял кредитную карту и зарплатный счёт (2 новых продукта);
- топ‑7 модели: карта на 1-м месте, ипотека, …, зарплатный на 5-м;
- Precision@7 учитывает, что 2 из 7 предложений верные;
- Recall@7 — что оба реальных новых продукта попали в семёрку;
- MAP@7 дополнительно награждает то, что карта стоит **выше** в списке.

##### Дополнительно (по возможности)

- Метрики **по отдельным продуктам** или усреднение с равным весом редких и частых продуктов — чтобы модель не «выигрывала» только за счёт самых популярных продуктов (текущий счёт и т.п.).
- Доля клиентов **без единой** верной рекомендации в топ‑7 — грубый индикатор «пустых» офферов.

##### Что сознательно не берём как главную метрику

- **Accuracy** («доля правильных 0/1 по всем продуктам») — почти всегда высока из‑за кучи нулей (клиент не берёт большинство продуктов) и плохо отражает качество списка.
- **ROC-AUC по одному продукту** — полезна для отладки одной модели «да/нет», но не отвечает на вопрос «хорош ли топ‑7 для кросс-сейла».

##### Где какие метрики живут

| Где | Какие |
|-----|--------|
| Обучение / MLflow | MAP@7, Precision@7, Recall@7 (и при необходимости разбивка по продуктам) |
| Файл `models/metrics.json` | снимок тех же офлайн-метрик лучшего прогона |
| Прод-сервис (`/metrics`, см. `monitoring/metrics.md`) | **не** MAP@7, а служебные: число запросов, задержки, ошибки — качество модели в проде отдельно не считается без разметки новых покупок |

Итог для сдачи: в README и экспериментах фиксируем **MAP@7 как основную**, Precision@7 и Recall@7 — как поясняющие; K согласован с API (`top_k`).

#### 1.4. Схема валидации

Данные делим **по времени** (поле `fecha_dato`), а не случайно по строкам или клиентам.

Признаки всегда берутся из месяца **t**, правильные ответы — из **t+1**. В проверку не должны попадать факты из будущего относительно признаков.

##### Почему не случайный split и не k-fold по строкам

- Задача про прогноз на **следующий месяц**, а не про случайную строку таблицы.
- При случайном разделении соседние месяцы одного клиента легко оказываются и в обучении, и в проверке — метрики завышаются (**утечка**).
- В проде модель всегда смотрит **вперёд по времени** — так же нужно проверять качество.

##### Как режем данные

Логика (точные даты подтвердим после EDA — какие значения `fecha_dato` есть в файле):

| Часть | Роль | Идея |
|-------|------|------|
| **Train** | обучение | более ранние месяцы; для каждого t цель — новые продукты в t+1 |
| **Valid** | выбор модели и настройка | следующие месяцы по тому же правилу t → t+1 |
| **Holdout** (желательно) | финальная оценка «как в проде» | самый поздний доступный период; смотрим один раз |

Черновые границы уже есть в `configs/train.yaml` (`split.train_end`, `split.valid_end`) — после EDA их нужно сверить с реальными месяцами.

##### Правила без утечки

1. В признаках на t нет полей и сводок, посчитанных по t+1 и позже.  
2. История и динамика — только из месяцев **не позже t**.  
3. Один и тот же клиент может быть и в train, и в valid в **разные** месяцы — это нормально: запрет не на id, а на заглядывание в будущее.  
4. `random_seed` фиксируем для обучения модели, но **нарезку по времени им не рандомизируем**.

##### Что считаем на valid / holdout

Для каждого клиента-месяца из проверочной выборки:
- строим топ‑K из продуктов, которых не было на t;
- сравниваем с фактом переходов `0 → 1` в t+1;
- усредняем **MAP@7**, **Precision@7**, **Recall@7**.

##### Почему не «отложить 20% клиентов»

Разделение только по `ncodpers` хуже имитирует прод: банк каждый месяц скорит **тех же** клиентов на новых срезах. Главный риск здесь — **время**, а не пересечение id. Отдельную проверку на совсем новых клиентах можно добавить позже.

**Итог:** time-based split по `fecha_dato` — учимся на прошлом, проверяем на будущем, без утечки из t+1; метрики — MAP@7 / Precision@7 / Recall@7 на топ‑K.

#### 1.5. Формат ответа API

Внешнее приложение (CRM, личный кабинет, кампания) передаёт id клиента и получает **короткий упорядоченный список** продуктов, которых у него ещё нет.

##### Запрос

```http
POST /recommend
Content-Type: application/json
```

```json
{
  "ncodpers": 15891,
  "top_k": 7
}
```

| Поле | Обязательно | Смысл |
|------|-------------|--------|
| `ncodpers` | да | id клиента — как в датасете |
| `top_k` | нет | сколько позиций вернуть; по умолчанию из `configs/service.yaml` (сейчас 7) |

Позже можно добавить батч (`ncodpers` списком) — на первом этапе не обязательно.

##### Ответ (успех)

```json
{
  "ncodpers": 15891,
  "top_k": 7,
  "recommendations": [
    {"product": "ind_recibo_ult1", "score": 0.82},
    {"product": "ind_tjcr_fin_ult1", "score": 0.71}
  ]
}
```

| Поле | Смысл |
|------|--------|
| `recommendations` | список по убыванию `score`, длина ≤ `top_k` |
| `product` | код колонки `ind_*_ult1` — однозначная связь с данными и моделью |
| `score` | оценка модели (чем выше, тем приоритетнее предложение) |

Уже имеющиеся у клиента продукты в список **не входят** (фильтр после модели).

##### Служебные эндпоинты (уже в каркасе)

| Метод | Путь | Зачем |
|-------|------|--------|
| `GET` | `/health` | проверка, что сервис жив (Docker / балансировщик) |
| `GET` | `/metrics` | метрики для мониторинга (Prometheus) |
| `GET` | `/docs` | интерактивная схема FastAPI |

##### Ошибки (контракт)

| Ситуация | Код | Идея ответа |
|----------|-----|-------------|
| клиента нет / нет признаков | `404` | понятное сообщение; пустой список не выдаём под видом успеха |
| невалидный JSON / нет `ncodpers` | `422` | ошибка валидации FastAPI / Pydantic |
| модель не загружена / внутренняя ошибка | `500` | без деталей устройства модели наружу |

##### Почему такой формат

1. **`ncodpers`** — нативный ключ датасета, без лишнего преобразования.  
2. **`product` = код `ind_*_ult1`** — стабильный контракт с обучением; «человекочитаемое имя» можно отдавать в UI/CRM отдельным справочником или встроить отдельным полем. В доступных данных проекта такого справочника по умолчанию нет, поэтому игнорируем.  
3. **`score` в ответе** — может понадобиться в дальнейшей обработке: использовать в фильтрах, сравнивать варианты, показывать приоритет.  
4. **`top_k` в запросе** — разным каналам нужен разный лимит (пуш vs звонок).  
5. **Не отдаём уже имеющиеся продукты** — соответствует целевому действию «новый продукт».

##### Пример вызова (после продуктивизации)

```bash
curl -s -X POST http://localhost:8000/recommend \
  -H "Content-Type: application/json" \
  -d "{\"ncodpers\": 15891, \"top_k\": 7}"
```

### 2. Инфраструктура обучения (MLflow)

Для трекинга экспериментов поднимается **MLflow Tracking Server** с Model Registry. Схема такая же, как в спринте 2 курса:

| Компонент | Где хранится | Назначение |
|-----------|--------------|------------|
| Backend store | PostgreSQL (личная БД курса) | runs, параметры, метрики, теги |
| Model Registry | та же PostgreSQL | версии зарегистрированных моделей |
| Artifact store | S3 (Yandex Object Storage) | файлы моделей, графики, отчёты |
| UI | `http://127.0.0.1:5000` | просмотр экспериментов |

#### Переменные окружения

Секреты **не коммитятся**. Шаблон — [`.env.example`](.env.example), рабочий файл — `.env.local` (или `.env`).

Нужные ключи:

- `DB_DESTINATION_*` — хост/порт/БД/логин/пароль личной PostgreSQL;
- `S3_BUCKET_NAME`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`;
- `MLFLOW_S3_ENDPOINT_URL` (по умолчанию `https://storage.yandexcloud.net`);
- `MLFLOW_TRACKING_URI` для клиентов обучения (по умолчанию `http://127.0.0.1:5000`).

Имя эксперимента задаётся в `configs/train.yaml` → `mlflow.experiment_name` (`bank-product-recommender`).

#### Запуск

Скрипты упаковывают весь старт сервера (требование task.md — `.sh` с запуском и настройкой):

```bash
# предпочтительно на Windows
python scripts/start_mlflow.py

# Git Bash / WSL / Linux VM курса
bash scripts/start_mlflow.sh
```

Что делают скрипты:

1. Читают `.env.local` (если нет — `.env`).
2. Проверяют наличие обязательных переменных.
3. Собирают `backend-store-uri` / `registry-store-uri` вида  
   `postgresql://USER:PASSWORD@HOST:PORT/DB?sslmode=require`.
4. Задают `default-artifact-root=s3://S3_BUCKET_NAME` и `MLFLOW_S3_ENDPOINT_URL`.
5. Стартуют `mlflow server` на `0.0.0.0:5000` с флагом `--no-serve-artifacts` (артефакты читаются/пишутся напрямую в S3).

После старта UI: http://127.0.0.1:5000  
Клиенты обучения (`notebooks/02_experiments.ipynb`, `src/models/train.py`) подключаются через `MLFLOW_TRACKING_URI` / `configs/train.yaml`.

#### Зависимости для сервера

В `requirements.txt` добавлены `boto3` (S3) и `psycopg2-binary` (PostgreSQL), плюс сам `mlflow`.

#### Опционально: локальный Docker без облака

`docker compose up -d mlflow` поднимает упрощённый сервер на SQLite и volume — удобно офлайн, но **для сдачи ориентируемся на PostgreSQL + S3** через `scripts/start_mlflow.*`.

#### Объём и структура

| Показатель | Значение |
|------------|----------|
| Строк | ~13.6 млн |
| Месяцев (`fecha_dato`) | 17: с `2015-01-28` по `2016-05-28` |
| Клиентов в месяце | ~625 тыс. → ~931 тыс. |
| Пересечение клиентов соседних месяцев | ~99.7% |

В июле 2015 база резко расширяется (~632 тыс. → ~830 тыс. клиентов). Один клиент даёт много объектов во времени — случайное перемешивание строк при валидации недопустимо.

#### Целевое действие

Сравнивались соседние месяцы t и t+1. Новый продукт — переход **`0 → 1`**.

| Показатель | Значение |
|------------|----------|
| Доля клиентов ≥1 нового продукта за месяц | ~3.6% в среднем |
| Среднее число новых продуктов на клиента | ~0.045 |
| Медиана / 95-й / 99-й процентили | 0 / 0 / 1 |

Кросс-сейл редкий: у большинства клиентов за месяц нет ни одного открытия. Метрика «доля правильных 0/1 по всем продуктам» бесполезна. Ориентир — качество короткого списка (**MAP@7**, Precision@7, Recall@7); `top_k=7` покрывает типичные факты с запасом.

#### Продукты: владение ≠ открытия

Чаще всего **уже есть** текущий счёт (`ind_cco_fin_ult1`, ~66%), затем особый счёт и recibo (~13%). Редкие продукты (гарантии, сбережения) — доли процента.

По **первым открытиям** лидируют иначе: `ind_recibo_ult1`, зарплатный/пенсионный счета, кредитная карта, текущий счёт. Ипотека и сбережения почти не открываются. Модель легко перекосится в сторону массовых продуктов — качество стоит смотреть и в целом, и по продуктам.

#### Качество полей

- `conyuemp`, `ult_fec_cli_1t` — пустые на ~99.9% → не используем.
- `renta` — пусто ~20.5% → заполнение + признак «доход неизвестен», удобен логарифм.
- Полезные кандидаты в признаки: `sexo`, `segmento`, `tiprel_1mes`, активность клиента, регион, текущий портфель.
- `canal_entrada` — много редких значений → укрупнять категории.
- `age` / `antiguedad` / `renta` часто приходят текстом → обязательная чистка в `prepare`.

#### Разделение по времени

Даты из `configs/train.yaml` есть в данных:

| Часть | Месяцы t (признаки); ответ из t+1 |
|-------|-------------------------------------|
| Train | `2015-01-28` … `2015-12-28` |
| Valid | `2016-01-28` … `2016-04-28` |
| Не объект обучения | `2016-05-28` (нет следующего месяца с ответом) |

При желании последний pairable-месяц (`2016-04-28`) можно выделить в отдельный holdout, а valid сократить до янв–мар 2016.

#### Что берём дальше

1. Пайплайн `prepare`: стыковка t → t+1, чистка профиля, план из `eda/09_cleaning_plan.json`.
2. Признаки: профиль + портфель на t (+ лаги по возможности).
3. Модель и API: ранжирование топ-K, фильтр уже имеющихся продуктов.
4. Baseline для сравнения: «самые часто открываемые продукты» — из-за сильного дисбаланса.

### 4. Признаки и обучение

Ноутбук экспериментов: [`notebooks/02_experiments.ipynb`](notebooks/02_experiments.ipynb).  
Журнал экспериментов: [`suggestions_04.md`](suggestions_04.md).  
Код: `src/data/prepare.py` → `src/features/build.py` → `src/models/train.py`.  
Рабочая модель: **v7** → `models/model.bin`, метрики → `models/metrics.json`.

#### Как запускать

```bash
python scripts/start_mlflow.py   # Tracking Server (PG + S3), опционально
python -m src.data.prepare --config configs/train.yaml
python -m src.features.build --config configs/train.yaml
python -m src.models.train --config configs/train.yaml
# без MLflow: --skip-mlflow
```

Сэмпл в `configs/train.yaml`: **100 000** клиентов/мес train, **133 333** valid (`random_seed: 42`).  
Это ≈ 1.2M / 0.53M строк. Значение `0` = без лимита.

#### Признаки (43)

| Блок | Что вошло |
|------|-----------|
| Профиль | `age`, `antiguedad`, `renta` (log1p) + `renta_missing`, активность, `ind_nuevo`, `indrel`, `cod_prov` |
| Категории | частотное кодирование `sexo`, `segmento`, `tiprel_1mes`, `nomprov`, …; для `canal_entrada` — топ‑N + «прочее» |
| Портфель на t | 24 флага `has_ind_*` + `n_products` |

Таргет — 24 бинарных перехода `0→1`. Уже имеющиеся продукты в рекомендации не попадают.  
Полные лаги портфеля пробовались (121 признак) — MAP@7 не вырос, в финале выключены.

#### Модель (финальная v7)

1. **Baseline** — рейтинг продуктов по частоте открытий на train.  
2. **LightGBM per-product** + **hybrid**: если позитивов &lt; `min_positives_train=100` → score = popularity.  
3. **Early stopping** по последнему месяцу train (не по final valid): patience=20, потолок 300 деревьев.  
4. Ранжирование: scores → фильтр портфеля → **топ‑7**.

Time-split: train t = янв–дек 2015, valid t = янв–апр 2016.

#### Результаты на valid (сэмпл 100k, 533 332 строк)

| Модель | MAP@7 | Precision@7 | Recall@7 | lift к baseline |
|--------|------:|------------:|---------:|----------------:|
| Popularity baseline | 0.02072 | 0.00568 | 0.03059 | — |
| **v7 LightGBM + hybrid + ES** | **0.02566** | 0.00569 | 0.03070 | **+23.8%** |

Доля строк valid хотя бы с одним новым продуктом ≈ **3.2%** — абсолютные @K низкие; ориентир — прирост к baseline.

По продуктам лучше всего: `nomina` / `nom_pens`, `tjcr`, `cno`, `ecue`, `recibo`, `cco` (AUC ≈ 0.90–0.96).  
9 редких продуктов (в т.ч. `plan`, `ctju`) → popularity (hybrid).

Что **не** сработало (см. `suggestions_04.md`): `scale_pos_weight`, полные лаги портфеля.

#### Что видно в MLflow

- params: `top_k`, LightGBM, `min_positives_train`, early stopping, размеры выборок;  
- metrics: `baseline_*` / `model_*` @7, AUC по продуктам;  
- artifacts: `train/model.bin`, `train/metrics.json`.

#### Выводы

1. Пайплайн согласован с постановкой (time-split, топ‑K, фильтр портфеля, без look-ahead).  
2. Финальная модель стабильно лучше popularity (**MAP@7 +24%** на текущем сэмпле).  
3. Главный ограничитель — редкость `0→1` и хвост продуктов; hybrid + ES дают осторожный прирост без переобучения под valid.  
4. Сервисный артефакт: `models/model.bin` (joblib: модели + popularity + maps + feature_columns).
